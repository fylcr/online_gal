# Design

## Context

`packages/engine-api/src/types.ts` 定义了 `GameSource` 的目录枚举、整文件读取、范围读取、类型与大小查询。`packages/core/src/library.ts` 的 `openSource()` 根据来源描述打开本地数据。`packages/vfs/src/host-source.ts` 已能从 `GameSource` 接入 KiriKiri 的字节读取路径。新来源沿用这三处边界和现有可写覆层。

已核对官方仓库的 `src/backend/router.ts` 和 `src/backend/routes/fs.ts`。当前可用入口为 `POST /api/fs/list` 和 `POST /api/fs/get`，列表数据包含 `content`、`total` 和可能的 `page_size`，文件元数据包含 `size`、`is_dir` 和 `raw_url`。接口可能用 HTTP 200 携带失败的 JSON `code`。默认的跨域配置仅允许同源。下载链和所用存储驱动能否在浏览器中提供可读的 Range 响应，须按第 1 节实测。

## Goals / Non-Goals

- 通过自托管 OpenList-Worker 服务挂载远程只读游戏目录，复用现有引擎的来源打开、归档和覆层路径。开发、候选验收和生产均遵循 `openspec/config.yaml` 的 Cloudflare Workers 用途约束。
- 每日解析官方仓库默认分支，验证候选制品和生产部署的实际契约。每日运行状态、失败操作和待发布候选可追踪。
- 本次范围为远程游戏读取。存储管理、上传和新的用户登录流程属于独立变更。

## Decisions

### 1. 自托管 Node.js 服务和文件接口适配

OpenList-Worker 使用上游自托管入口。已核对上游 `package.json` 和 `.github/workflows/build-verify.yml`，当前 `pnpm run build` 产出 `dist-server/api/[...route].js`，`pnpm start` 启动 Node.js 服务。每次从当日解析出的候选提交读取构建与启动说明。在普通 Node.js 主机或容器提供 HTTPS，隔离候选与生产各用独立服务和数据配置。按任务 1.1 验证服务启动、持久化配置、所用存储驱动和对应源码提供方式。

Online Gal 通过 `packages/vfs/src/openlist-source.ts` 消费 OpenList 的文件 HTTP 接口。该适配器负责请求、响应解码、分页、下载链接和错误映射。`packages/core/src/types.ts` 与 `packages/core/src/library.ts` 负责持久化来源标识并重新打开该来源。

- 来源描述保存配置中的服务标识及规范化游戏根。适配器复用项目的路径规范化和根目录边界检查。列表只枚举直接子项，遍历分页直至完整，并对未前进或不一致的分页明确报错。类型和大小来自元数据。HTTP 状态和 JSON `code` 均检查，网络、限流、接口和权限错误单独报告。
- 浏览器从配置的 OpenList HTTPS 服务读取。生产 CORS 允许 Online Gal 站点，隔离环境使用专用测试来源。服务和存储端的读取权限限定到发布的游戏根。列表、元数据、下载地址和允许的重定向都在实际浏览器中验证。若上游配置允许，把下载固定在已配置的 OpenList origin 上。存储管理凭据只留在服务端配置，来源描述、缓存和日志只记录非敏感配置。签名下载 URL 仅用于当次读取，过期时通过元数据接口重新获取。
- 以固定夹具对所用驱动验证 `Range`。当可用时，校验 `206`、`Content-Range`、响应体长度和测试字节。CORS 配置必须让浏览器实际读取这些字段。范围不可用时，报告来源能力或读取错误。整文件读取和降级读取遵守明确的字节预算，下载过程中超出预算即取消读取。归档和 KiriKiri 的读取沿用现有 `GameSource` 接入点。

### 2. 每天跟踪官方默认分支

在 GitHub Actions 配置每日定时和手动补跑入口。时间选用非整点 UTC。每次走官方仓库的元数据和分支引用解析当前 HEAD，以当次 SHA 构建候选，或者复用该 SHA 可追溯且摘要匹配的候选制品。SHA 与制品摘要记录在该次运行和部署中。下一次运行重新解析官方分支。现有 `.github/workflows/check-upstream-drift.yml` 的调度做法可复用，OpenList-Worker 使用单独的跟踪流程。

当天分别实测候选和生产 OpenList 服务。上游查询失败时仍尽量取得生产接口结果，并将整个巡检记为失败。两个目标分别使用测试夹具和各自的部署标识。记录 UTC 时间、默认分支、HEAD、候选与生产部署标识、制品摘要、每项结果和失败类型。启用失败通知和独立于此任务的运行新鲜度检查，使超出日检窗口的缺跑可见，手动重跑会补记结果。

### 3. 发布使用同一个已验收制品

候选构建与生产发布使用独立任务和权限。隔离服务只使用专用测试数据和凭据，生产部署凭据只进入项目控制的发布任务。发布时核对隔离验收通过的制品摘要。生产服务串行更新，避免较晚完成的旧候选覆盖更新版本。用 Node.js 主机或容器平台的发布工具部署和回退，以部署版本或镜像摘要追溯。

候选通过后进入生产发布流程。生产部署后立即跑同一份契约测试，最后通过的部署标识用于故障回退。会改变存储结构的上游更新须先用隔离数据验证升级及恢复。发布后复测失败就回退并复测，结果写入运行记录。候选接口发生变化时，按告警指出的提交和操作修复适配器，再用当天解析的候选验收。巡检每天继续运行。

### 4. 实施归属

`file-system` 会话负责本变更的 VFS、来源打开契约、测试和日检流程。`packages/core` 或 `apps/app` 中已有负责人的文件，由对应负责人按该契约接入。Node.js 主机或容器平台、隔离与生产地址、专用存储配置和发布权限由文件系统会话按团队分工协调。

## Risks / Trade-offs

- 上游、存储驱动与 CDN 都可能改变下载行为。真实浏览器同时验证候选和生产，单元夹具负责复现不同错误。生产告警用于发现巡检间隔内已经发生的故障。
- 上游分支改动可能包含数据迁移。隔离环境验证升级和恢复，生产保留可回退部署及必要的数据恢复依据。
- GitHub 定时任务可能延迟或缺跑。运行记录和独立的新鲜度检查覆盖该情况，手动入口用于立即补跑。

## Migration Plan

1. 在隔离 Node.js 服务配置与生产目标一致的存储驱动，用合成数据验证 API、CORS 与 Range。
2. 接入 VFS 来源、现有打开路径和可写覆层，完成候选及生产共用的契约套件。
3. 上线每日巡检、告警和发布门禁。首次生产发布使用已验收的候选并立即复测，记录首个可恢复部署。
4. 后续更新按候选验收、发布复测、必要时回退的顺序执行。
