### KiriKiri：取数来源已接上 `@online-gal/vfs`（接缝就位并已验证）

**接缝要盖两件事，不是一件**（原指南「所有取数都在 `vlfs.js`」的说法不完整）：

1. **字节**——`platforms/web/vlfs.js` 里 `hostByteSource()` 读 `window.__onlineGalVfsSource`，
   装了它则三处远程读（`_readSource` 的 `case 'remote'`、`_readZipSourceBytes`、`_readZipSourceStream`）
   全走它，不再自己 `fetch`；没装时与参考实现一致。
2. **尺寸**——`platforms/web/shell.html` 判断「能不能 Range 懒加载」**只靠 `fetch(url, {method:'HEAD'})`**。
   平台来源（OPFS / FileSystemAccess / 压缩包内的文件）根本没有 URL 可 HEAD，
   不知道尺寸就会退化成「整包下载」。所以 shell 里新增 `hostSourceStat(url)`：
   宿主对象提供 `stat` 时由平台回答尺寸与 ETag，否则原样回退到 HEAD。

两处补丁都由**同一个幂等脚本** `ports/krkr/kirikiroid2/patch-vlfs-host-source.mjs` 打
（各自 `git checkout` 还原后再打，重复执行字节一致），`run-build.sh` 在配置前调用。
产物里已经带着补丁：`vlfs.js` 60,605 → **64,025 B**，`shell.html` 100,605 → **102,990 B**，
生成的 `index.html` **53,504 B** 里能 grep 到 `hostSourceStat`。

#### 这条通道上的四个坑（都会伪装成「引擎没起来」）

1. **`pageId` 必须是数字，不是字符串。** 传 `"1"` 会被参数校验拒绝：
   `MCP error -32602: Input validation error: Expected number, received string at pageId`。
   而 `new_page` 返回的是**散文**（"Page 1 created…"），从里面正则抠出的天然是字符串，必须 `Number()`。
2. **页面要用 `list_pages` 选，不能用 `new_page` 的返回。** 冷启动时浏览器自带一个新标签页，抠到的 id
   可能属于它，报告就变成 `title: 新标签页`、`isolated: false`、`canvas: none`——看着像引擎没启动。
   更麻烦的是 `new_page(url)` 加一次 `navigate_page` 会留下**两个同 URL 的标签页**，只有 `[selected]`
   那个是引擎的（`title: krkr2`），另一个仍是 shell 的长 HTML 标题。选择顺序：选中的 → 标题为 `krkr2` 的
   → 任意该 URL 的。
3. **页面 id 在长任务里会失效。** 引擎引导期间标签页可能被替换，之后用旧 id 调用报 `Error: No page found`，
   同样像「模拟器挂了」。**每次页面级调用前重新 `list_pages` 解析一次**即可根除。
4. **`evaluate_script` 的返回值是双层编码的。** 工具把返回值包在 ```` ```json ```` 里，而页面函数又返回
   `JSON.stringify(...)`，所以解析一次得到的是**字符串**；`value.archiveBytes` 于是 `undefined`，报告打成
   `?` / `0`——**恰好读成「一个字节都没读」这个相反结论**。解析后再判断 `typeof === 'string'` 解一层。

#### 硬性约束：同一时间只跑一个实例

**一个浏览器只能跑一个 krkr 模拟，不要开多个窗口。** 同时开两个实例（例如既留着手写的可见窗口、又让 MCP
拉起自己的 Chrome）会互相干扰：实测出现过页面 id 错乱与 `No page found`。收工时按 profile 精确关闭：

```bash
# 只关这两个专用 profile，不动用户自己的浏览器
Get-CimInstance Win32_Process -Filter "Name='msedge.exe' or Name='chrome.exe'" |
  Where-Object { $_.CommandLine -match 'kiri-visible|chrome-mcp-profile|remote-debugging-port=922' } |
  ForEach-Object { taskkill /T /F /PID $_.ProcessId }
```

**这条通道踩到的坑（都写进脚本注释了，恢复时省时间）：**

1. **`take_snapshot` 要求 `pageId` 是数字**，传字符串会被 MCP 输入校验直接拒绝（`Expected number, received string`）。
   而 `new_page` 是**再开一个**标签，`list_pages` 里要取 `[selected]` 那行——取第一个会拿到 `chrome://new-tab-page`。
2. **`<input type=file>` 在 a11y 树里是 `button`**（带 `value="未选择任何文件"`），不是 `input`；
   按标签名找永远找不到。本页正好两个（文件夹在前、压缩包在后），取最后一个。
3. **`upload_file` 会被工作区根拒绝**：`Access denied: … is not within any of the configured workspace roots`。
   根来自 MCP 标准的 `roots` 能力——客户端要在 `initialize` 里声明 `capabilities.roots` 并**应答 `roots/list`**
   （它是个服务端→客户端的 *请求*，不答就等于没有根）。`mcp-app-flow.mjs` 现在回 `file:///D:/online_gal`。
4. **这台机器的 Chrome 是持久 profile**，而 shell **同一站点只允许一个引擎**（`Engine Already Running` 弹窗，
   用共享存储做锁）。前一轮留下的页面还占着锁时，新页面会「帧挂上、归档甚至已经通过接缝解析完，但引擎被拒」——
   我一开始把它误读成引擎卡在 `Preparing engine... (3 remaining)`。**解法：`new_page` 传 `isolatedContext`**，
   每轮一份干净存储（等价于 Edge harness 每次用新 profile）。
5. 持久 profile 里还会留下 shell 注册的 **service worker**（`/krkr2-web/` 作用域 + `krkr2-<版本>` 缓存）。
   隔离上下文能绕开它；脚本同时把「SW 注册与缓存」记进报告，便于判断某次结果是缓存还是真跑。

**这一层抓出了三个只有真跑才会暴露的问题，都已修：**

1. **归档被「展开掉」**：`GameLibrary.combine()` 只把归档的内容挂成层，归档**文件本身**在虚拟树里不可见。
   于是引擎的挂载探针在源里找不到任何归档 → 退回解释器。修法：归档同时作为**文件**可读
   （放在最后一层，内容层优先），`FileListSource` 直接用那些 blob。**首个失败点是
   `?game=` 的 404**，根因就在这。
2. **`eager/lazy` 判定必须在取数时做**：`loadMode` 在**脚本执行期**解析，而接缝要等 frame 的 `load`
   才装上——解析期的「有没有接缝」永远看不到，于是走了 eager 分支去下载一个客户端来源根本没有的 URL。
   修法：补丁新增第 5 条 shell 修改，在 `fetchAndExtractZip` 里**取数时**再判一次。
3. **接缝装得太晚（重载必崩）**：即便 (2) 修了，shell 仍在脚本执行期读接缝（重载后 frame 是新窗口，
   只认自己窗口的接缝永远来不及）。修法：`vlfs.js` 与 `shell.html` 的接缝助手都**回退到同源父窗口**
   （`window.parent.__onlineGalVfsSource`），`createKiriPage` 在建帧时就把源发布到**嵌入页的 window**上
   （用 `document.defaultView` 而不是 `globalThis`，免得 jsdom 下污染 Node 全局），`dispose()` 两处都清。

顺带修掉两个截图/UI 暴露的小问题：**压缩包根本无法被选中**（唯一的 file input 带 `webkitdirectory`，
浏览器里选不了 `.zip`；已新增一个不带该属性的压缩包 input 并把按钮标为「选择压缩包」），
以及 **`RUNTIME_LABELS` 缺 `krkr2-wasm`/`onscripter-wasm`**（UI 会直接显示原始 id）。
（诚实限定：这个 harness 的宿主源内部仍是 HTTP Range 取数——它是一个**接线替身**，用来证明 shell 真的把
尺寸与字节交给了宿主、并证明按需读取；真正「不碰网络」的来源要等 OPFS/FSA 版接入。）

### 浏览器实测抓到并修掉的两个 bug（都是接缝自身的，单元测试看不见）

1. **blob 型 zip 源被误导向宿主**：`assets.zip` 走 `registerZipBlob`，它的 source 只有 `blob`、**没有 `url`**，
   于是宿主收到 `readRange(undefined, …)` → `range 404 undefined` → 整页退回落地页。
   修法：`_readZipSourceBytes` / `_readZipSourceStream` 的宿主分支加 `source.kind !== 'blob'` 守卫
   （blob 字节本来就在本地，没有理由问宿主）。
2. **`?game=` 默认的 eager 分支根本不问宿主**：它直接整包 GET 进 OPFS，对「平台本地已有字节」的来源
   既浪费又不可行（没有可 GET 的 URL）。修法：`loadMode` 解析后，若**页面装了宿主对象且调用方没显式指定
   `loadMode`**，默认改成 `lazy`（显式 `loadMode=eager` 仍生效），于是挂载走已经补好的 `hostSourceStat` 路径。

### Provider 外壳已就位（本轮完成）

`packages/runtime-kag/src/wasm-provider.ts` 的 **`kirikiriWasmProvider`**（`runtimeId: 'krkr2-wasm'`、
**`priority: 105`**）已注册进 `packages/core/src/platform.ts` 的 `BUILTIN_PROVIDERS`，**排在解释器 `krkr2` 之前**
（实测顺序：`krkr2-wasm > krkr2 > onscripter-wasm > …`）。它复用 `probeKirikiri`，所以两者对「什么是 KiriKiri 游戏」
永远不会分歧。

`packages/runtime-kag/src/wasm-runtime.ts` 的 **`KiriWasmRuntime`** 照 `WebRuntime` 的形状包住 `createKiriPage`：

- iframe 就是呈现面（钉在宿主 canvas 上、黑底），**输入走 DOM 直达 iframe**，所以 `sendInput()` 是空实现；
- `tick()`/`render()` 空转（引擎自带循环；`render()` 只在未加载时刷黑底，并容忍 jsdom 下 `getContext('2d')` 返回 null）；
- `pause()`/`resume()` **诚实地什么都不做**——参考构建没有对外控制通道，假装能暂停只会误导；
- `save()`/`restore()` 与 ONS 同样理由：存档由 frame 里的引擎自己持有，宿主只记身份；
- `load()` 先校验 `pageUrl`/`gameKey`（缺则报出选项名、且**不建 frame**），再建 frame 并 `await ready()`，
  所以「页面没接上接缝」会变成 load 失败而不是静默挂起；
- `dispose()` 幂等、摘掉 frame，并清掉**两处**接缝（frame 窗口与嵌入页窗口）。

选项经 `gameConfig`（launcher 的通道）或类型化字段传入：`pageUrl`、`gameKey`、`param`（默认 `'game'`）、`resolveUrl`。

## 二、恢复工作的最短路径

```bash
# 一条命令即可：脚本内含全部必需变量、overlay 端口安装、bison 数据目录、SDK 拼写统一与端口预热
bash /d/online_gal/ports/krkr/kirikiroid2/run-build.sh
```

**实测：退出码 0，产出五个产物；再跑一次同样退出码 0 且不重编任何东西。**

脚本现在会自动做这些事（顺序有意义）：

### 2. vcpkg 端口解析机制：builtin 注册表读 **git 对象库**，不读工作区（最重要的一条）

**现象**：把 `.patch` 放进 `.ref/vcpkg/ports/gettext/` 并追加到 `portfile.cmake` 的 `PATCHES` 列表后重跑，
gettext 仍然只应用 7 条补丁，`patch-x64-mingw-static-7-err.log` 不出现，解包目录名（由补丁集哈希决定）
也**没有变化**。`.ref/vcpkg` 的 `HEAD` = `b1e15efe`，而 `$REPO/vcpkg-configuration.json` 里
`"default-registry": {"kind":"builtin","baseline":"b1e15efe..."}`——**baseline 就是 HEAD**。

**判据（可复用，一行定量结论）**：`buildtrees/<port>/<triplet>.vcpkg_abi_info.txt` 记录了 vcpkg 实际读到的
每个文件的 sha256。对 gettext / pkgconf，其中 `portfile.cmake` 一行**等于 `git cat-file blob HEAD:...`**，
而不是磁盘上改动后的文件；新增的未跟踪 `.patch` 连 ABI 输入都不是。

**顺带纠正一处历史误判**：`.ref/vcpkg/ports/pkgconf/portfile.cmake` 那处长期存在的 `M` 改动
（原指南写「构建脚本所加，勿回退」）**从未生效过**——它的 ABI 记录同样等于 HEAD blob。
它无害，但不要把它当成功原因；真正解决 pkgconf 的是宿主 triplet 改成 `x64-mingw-static`。

**对照**：overlay 端口是按**文件系统**读取且优先的。同样用 ABI 哈希验证：`ffmpeg` 与 `glib` 记录到的
`portfile.cmake` 哈希**等于** `.ref/kirikiroid2-web/vcpkg/ports/<port>/portfile.cmake`。
所以本机唯一能改端口行为的通道是 overlay 端口（`vcpkg-configuration.json` 的 `overlay-ports`）。

**修法**：`ports/krkr/kirikiroid2/overlay-ports/<port>/` 放完整端口目录（源），`run-build.sh` 在配置前
`rm -rf` + `cp -r` 到 `$REPO/vcpkg/ports/<port>`（幂等，可重跑；`.ref` 保持钉住状态）。

### 3. `libexif`：Emscripten 目标下 `vcpkg_configure_make` 不加 `--host`

**现象**：`configure: error: cannot run C compiled programs. If you meant to cross compile, use '--host'.`

**根因**：`vcpkg_configure_make` 只在 `VCPKG_TARGET_IS_WINDOWS` 分支里推导 `--build/--host`
（`vcpkg_configure_make.cmake:410-439`），macOS/Linux 分支也不适用 Emscripten；而本仓库的
`wasm32-emscripten.cmake` 没设 `VCPKG_MAKE_BUILD_TRIPLET`。于是 autoconf 认为是本地构建，**运行** conftest。
Emscripten 产出的 conftest 是 CommonJS JS，而 Node 拒绝它——因为**项目根 `D:\online_gal\package.json`
声明了 `"type": "module"`，而 vcpkg 的 buildtrees 就在该目录下面**：

```
ReferenceError: require is not defined in ES module scope, you can use import instead
```

**修法**：overlay 端口 `ports/krkr/kirikiroid2/overlay-ports/libexif/` 在其 `portfile.cmake` 里
`vcpkg_configure_make` 之前加一行（`config.sub` 已确认接受该值）：

```cmake
set(VCPKG_MAKE_BUILD_TRIPLET "--host=wasm32-unknown-emscripten")
```

**不要**改 triplet 来修这个问题：triplet 内容参与 `triplet_abi` 哈希，一改所有 ~90 个 wasm 包全部失效重编。
`libexif` 是本依赖图里**唯一**走 autotools 的端口（`libgdiplus` 用 CMake），所以单端口 overlay 就够。

### 4. 参考仓库是 **shallow + partial(blob:none) + sparse-checkout**，`tests/` 与 `ui/` 根本不在工作区

CMakeLists 在 `if(WEB)` 下无条件 `add_subdirectory(tests/differential/wasmtime)`，UI 资源也要 `ui/cocos-studio`。

### 5. WinFlexBison：WinGet 的 symlink 让 bison 找不到 `data/m4sugar/m4sugar.m4`

**现象**：每个 bison 步骤都失败：

**根因**：WinFlexBison 按**被调用可执行文件所在目录**找 `data/`，而 CMake 调用的是

**修法**：`run-build.sh` 里定位真实包目录并导出（必须是 Windows 形式路径——win_bison 是原生程序，

```

### 6. **Emscripten 缓存被反复清空**：sanity 串随 SDK 路径拼写变化 → `cache.erase()`

**现象**：端口库（`libz.a`、`libSDL2-mt.a` …）与 `sysroot/lib/pkgconfig` 神秘消失；
`cmake --build` 报
`AssertionError: attempt to lock the cache while a parent process is holding the lock (sysroot\...\libfreetype.a)`
——emcc 在编译过程中被迫去构建端口，而端口构建又嵌套触发另一个端口构建。

**根因**：`tools/shared.py` 用 `expected = generate_sanity()` = `"<version>|<LLVM_ROOT>"` 与
`cache/sanity.txt` 比对，**不一致时不是警告而是 `cache.erase()`**
（`shared.py:430-435`，会打印 `(Emscripten: config changed, clearing cache)`），
连同 `cache/sysroot` 里所有端口库一起删掉。`LLVM_ROOT` 由 `EM_CONFIG` 所在目录 `$CFGDIR` 展开，
所以**同一路径的不同拼写就是不同的 sanity 串**。而 `run-build.sh` 预热阶段把 `EMSDK`/`EM_CONFIG`
写成 Git Bash 形式（`/d/emsdk`）、CMake 阶段写成 Windows 形式（`D:/emsdk`），且中途还 source
`emsdk_env.sh` 再改一次——两个阶段互相清空对方的缓存。

**判据**：`emcc --version` 打印的 `old sanity: ...` 与 `cache/sanity.txt` 内容对不上。

**修法**：全脚本只保留**一种**拼写（Windows 形式），在 source 完 `emsdk_env.sh` 之后再固定一次：

```bash
export EMSDK="$EMSDK_DIR_WIN"
export EM_CONFIG="$EMSDK_DIR_WIN/.emscripten"
```

### 7. Emscripten 不创建 `sysroot/lib/pkgconfig`，端口库建好即被丢弃

**现象**：每个端口的 `embuilder build ...` 都打印
`FileNotFoundError: ... cache\sysroot\lib\pkgconfig\zlib.pc`，且日志里端口库明明已经编译完成。

**根因**：`tools/ports/__init__.py:447` 取 `pkgconfig_dir = cache.get_sysroot_dir('lib/pkgconfig')` 后
**直接写文件、不建目录**；该目录只由 sysroot 头文件安装（`system_libs.py:2593`）作为副作用创建。
缓存刚被清空时，端口构建发生在 sysroot 安装**之前**，于是端口库生成成功却被整体丢弃。

**修法**：预热前先把目录建好并从 emscripten 自带的 pkgconfig 源拷入（`run-build.sh` 已加）。

### 8. 附带教训：`tail -3` 把真正的原因藏了整整两轮会话

预热循环原来是 `embuilder build $port 2>&1 | tail -3`，恰好把
`(Emscripten: config changed, clearing cache)` 和 `FileNotFoundError` 的行号上下文截掉，
只剩一句看不出所以然的 traceback 尾巴。现已放宽到 `tail -20`。
**排查 emscripten 问题时不要截断它的输出。**

## 八、恢复时的注意事项

- **`.test/` 与 `.ref/` 均已 gitignore**，参考仓库和测试脚本不入库。
- **改 `CMakeLists.txt` 后必须重跑 `cmake --preset`** 再构建。
- **构建前关闭 coi-server**，否则会提供旧 wasm。
- **`.ref/kirikiroid2-web` 不是完整工作区**：它是 shallow + `blob:none` partial clone + sparse-checkout
  （cone: `cmake cpp platforms/web vcpkg` + 本次补的 `tests/differential/wasmtime`、`ui`），
  且有 1807 个 skip-worktree 位——**受控目录缺失时 `git status` 依然干净**。
  怀疑「文件不见了」时先对账：`git -C .ref/kirikiroid2-web sparse-checkout list` 与
  `git ls-tree HEAD --name-only`，缺什么用 `git sparse-checkout add <dir>` 补。
- **`EMSDK` / `EM_CONFIG` 全流程只能有一种拼写**（本仓库统一用 Windows 形式 `D:/emsdk`）。
  拼写一变，emscripten 的 sanity 串就变，`check_sanity()` 会直接 `cache.erase()`
  把所有端口库删掉——症状是端口库莫名消失 + `attempt to lock the cache while a parent process
  is holding the lock`。判据：`emcc --version` 的 `old sanity:` 与 `cache/sanity.txt` 是否一致。
- **排查 emscripten 失败时不要截断它的输出**：`(Emscripten: config changed, clearing cache)` 与
  `FileNotFoundError: .../pkgconfig/*.pc` 都在被 `tail -3` 截掉的那几行里。
- **bison 用的是 WinGet symlink**（`...\WinGet\Links\win_bison.exe`），它旁边没有 `data/`，
  必须设 `BISON_PKGDATADIR` 指向真实包目录（Windows 形式路径）。
- **本项目根 `package.json` 是 `"type": "module"`**，而 vcpkg 的 buildtrees 就在它下面：
  Node 会把 emscripten/autoconf 产出的 CommonJS conftest 当 ESM 执行并报
  `require is not defined in ES module scope`。跨平台 autotools 端口必须拿到 `--host` 才会跳过 run test
  （见「本次会话」第 3 条）。
- **切换 emsdk 版本后必须用新的构建目录并重编所有依赖**（Emscripten 不保证跨版本 ABI 兼容）。
- **改动参考仓库源码的补丁脚本都应是幂等的、并从 git 还原起点**——本项目已在此栽过多次（多个 patcher 互相抹掉对方改动）。
- **Artemis 有三份东西，路径别写错**：`.ref/artemis` 是**官方 SDK 原件**（专有，可能不存在）、
  `.ref/artemis-official` 是**对它的逆向产物**（`reverse.sh` / `rebuild.sh` 生成，可重建）、
  `ports/artemis/src/` 是**重写后的引擎源码**（已入库，是源码不是产物）。
  旧位置 `.ref/artemis-official/rewrite/` **已删除**；`.ref/artemis-official/rewrite-sync/` 是
  同步口味的未入库副本（`.gitignore` 里的 `.ref/` 覆盖它）。
- **Artemis 的帧锚是相对量，不是绝对 hash**：好/坏判据 = **请求数 + lit 百分比 + frames 数**，
  `finalHash` 只在同一 session era 内可比（窗口尺寸一变 hash 就变）。`REWRITE.md` §1 的行为锚是
  `bef44818`；`p2-batch4-progress.md` 已明文作废「按 `finalHash == '550f7464'` 过滤」的做法。
- **`ports/artemis/vendor/artemis-sdk/` 是专有二进制，入库属于有意承担的风险**（见
  `THIRD_PARTY_NOTICES.md` 与 `docs/artemis-web-port.md` §15）。**再分发本仓库前应先删除该目录**，
  除非持有作者授权。删除后官方路线不可复现，但 `artemis/src/` 与平台代码不受影响。
