# The glue directory

Two generated files, the script that makes them, and the checker:

| file | what it is |
| --- | --- |
| `imports-map.md` | the readable table — every import the bridge module asks for, with its bucket, its signature, and two byte offsets into the official `artemis.js` |
| `imports-map.json` | the same table as data, for tooling and for diffing |
| `imports-map.mjs` | the generator; both files are its output and are not edited by hand |
| `verify-imports-map.mjs` | the independent checker; shares no code with the generator |

## Why this exists

The bridge module is a wasm2c rebuild of the official Artemis module. It asks its host
for **207 function imports** under a single module name `a`, whose field names are the
official glue's own minified keys — `$`, `Ob`, `Ea`, `xb`, and so on. Nobody can read
those names and know what a host has to build. This table is the answer: each of the
207 gets a bucket saying which modern host module decides it, and an offset saying where
in the official `artemis.js` the implementation of that call can be read.

The table is derived, not written. The import section is decoded out of the `.wasm`; the
correspondence from minified key to real Emscripten name is read out of the glue's
`asmLibraryArg` object; the nine runtime renames come from the build's own alias
manifest. Change an input and the table changes with it.

## Regenerating

```sh
ARTIFACT_DIR=<where you unpacked the artifact, see below>
node ports/artemis/harness/glue/imports-map.mjs \
  --wasm    "$ARTIFACT_DIR/dist/artemis-bridge/build/bridge.wasm" \
  --glue    ports/artemis/vendor/artemis-sdk/WebAssembly/asyncify/artemis.js \
  --aliases "$ARTIFACT_DIR/dist/artemis-bridge/build/runtime-imports.json"
```

That is the exact command the committed pair came out of. CI runs the same command into a scratch
directory in the step `Gate the committed import map against this build`, then hands both pairs to
`compare-imports-map.mjs` (see below) — a textual `cmp` is not what the gate does. If you regenerate
with anything else, the gate goes red for a reason that has nothing to do with the ABI.

**There is deliberately no `--forward`.** `imports-forward.c` is generated by the build and
is not tracked (`git ls-files` finds no `imports-forward`), so a clean checkout cannot
produce it and a command naming it is a command nobody can follow. Passing this build's copy
anyway flips every row's `forwarded` from `-` to `yes` and adds a summary line to the md —
about 200 lines of diff that record *how* a seam was implemented in that build, while every
other column records *what the module needs*. This table records the ABI.

`--forward` is still accepted, for the case where you are investigating the forwarders rather
than the ABI. With it, the `fwd` column is populated and the classification still stands on
the wasm import section plus the glue; the forwarders are corroboration, not an input.

Zero dependencies, node >= 20, ESM. Output is deterministic — no timestamps, no input
paths, nothing that depends on hash iteration order. Run it twice and `sha256sum -c` the
first run's hashes; both files compare OK.

The generator refuses to write anything rather than emit a table that looks complete but
is not. It exits non-zero if a row has no official name, no glue binding, or a `todo`
bucket with no reason; if a hand-written `todo` reason names an import that is not in
this build; if a bucket override names an import that is not in this build; or if a
classification rule matches no import at all (a dead rule means some name is riding the
fallthrough and nobody will notice).

## Getting the artifacts

`bridge.wasm` is not in the repository. It is built locally by
`ports/artemis/reverse/build-bridge-route.sh` — `bash ports/artemis/reverse/build-bridge-route.sh
[flavour] [outdir]` — which transpiles the official module with wasm2c, compiles it with em++ and
writes `bridge.wasm` into that `outdir`. CI runs the same script through
`.github/workflows/build-wasm-artemis-bridge.yml`, which downloads the result as the artifact named
by that workflow's `artifact-name` input.

Where the bytes land inside the artifact is not a constant of the reusable workflow; it is whatever
that caller passes as `artifact-dir` (`dist/artemis-bridge/build` for the bridge today, read the
caller's `with:` block rather than a path copied from here). Download it with:

```sh
gh run download <run-id> -n wasm-artemis-bridge -D "$ARTIFACT_DIR"
```

`$ARTIFACT_DIR` is any directory outside the tracked tree. The artifact carries four copies of the
module plus the generated `artemis.cpp`, so it is large and is never committed; pick somewhere you
are happy to delete. Its size is a property of the build, not a documented figure — measure it.

If you are not already authenticated, or `gh` cannot reach GitHub from where you are,
the repository is private and needs a token plus a proxy:

```sh
export HTTPS_PROXY=socks5://127.0.0.1:10808
gh auth login
```

There is no fixed hash to compare against. The module embeds its own build directory in the
runtime's assert strings, so a Windows checkout and a Linux runner produce different bytes from the
same tree (see below); the committed table records the hash of the module it was made from, which
is a provenance line and not a criterion. Compare your module against the one the table names only
to tell whether you are reading the *same build*, and expect a mismatch when you are not:

```sh
sha256sum "$ARTIFACT_DIR/dist/artemis-bridge/build/bridge.wasm"
grep -E '"moduleSha256"' ports/artemis/harness/glue/imports-map.json
```

`imports-map.md` records that hash in its own Provenance section, so a table and a binary can be
told apart or matched without trusting either one's filename. If the hash differs, the table was
generated from a different build and you should check whether the import surface moved — with the
comparer below, which decides that question on the ABI rather than the hash.

The glue (`artemis.js`) and the generated C (`imports-forward.c`, `runtime-imports.json`)
are side effects of the same run, unpacked next to `bridge.wasm`.

## Checking the output

The generator checks itself against its own inputs. A separate checker re-decodes the
import section with independent code and cross-checks the emitted table against that
decode and against the browser's own `WebAssembly.Module.imports`, so an error in the
generator cannot make its own output look right:

```sh
node ports/artemis/harness/glue/verify-imports-map.mjs \
  --wasm "$ARTIFACT_DIR/dist/artemis-bridge/build/bridge.wasm" \
  --glue ports/artemis/vendor/artemis-sdk/WebAssembly/asyncify/artemis.js \
  --json ports/artemis/harness/glue/imports-map.json \
  --md   ports/artemis/harness/glue/imports-map.md
```

Every judged check must pass; the run prints one line per check and a final verdict, and the
count is the checker's own business — read the verdict line rather than a number remembered
here. One further line reports the module's provenance without judging it (the module hash is
machine-dependent — see below). The checker is committed beside the table it checks, and it
reads the wasm and the glue itself rather than trusting anything the generator wrote.

### Comparing a regeneration against the committed pair

Regenerating is not the same question as checking. `imports-map.mjs` will write a table for
whatever bytes you hand it, and `verify-imports-map.mjs` judges a table against the module and
glue it is given — neither one answers "did this build's ABI move away from the committed
pair?". `compare-imports-map.mjs` is that question, and it is what CI runs:

```sh
OUT=$(mktemp -d)
node ports/artemis/harness/glue/imports-map.mjs \
  --wasm "$ARTIFACT_DIR/dist/artemis-bridge/build/bridge.wasm" \
  --glue ports/artemis/vendor/artemis-sdk/WebAssembly/asyncify/artemis.js \
  --aliases "$ARTIFACT_DIR/dist/artemis-bridge/build/runtime-imports.json" \
  --out-dir "$OUT"
node ports/artemis/harness/glue/compare-imports-map.mjs \
  --committed    ports/artemis/harness/glue/imports-map.json \
  --regenerated  "$OUT/imports-map.json" \
  --committed-md ports/artemis/harness/glue/imports-map.md \
  --regenerated-md "$OUT/imports-map.md" \
  --wasm         "$ARTIFACT_DIR/dist/artemis-bridge/build/bridge.wasm"
```

Exit 0 means the same ABI. It masks exactly four things and judges everything else exactly,
including fields nobody listed — that is the point of naming the mask instead of subtracting a
pattern from a diff:

| masked | why |
| --- | --- |
| `totals.moduleBytes`, `totals.moduleSha256` | machine-dependent; the module embeds its own build path |
| `rows[*].typeIndex` | renumbers when an unrelated import is added |
| `type#N` inside a row's `duplicate` | the ordinal counts duplicates within one build |
| the value cell of the md's `module bytes` / `module sha256` rows | same two hashes, in the readable table |

Judged strictly: row order, every function name and signature, every bucket, every glue offset,
every alias, the non-function imports with their limits, and the glue's own sha256 — a different
glue is a refusal, one line naming both files rather than a page of bad offsets. Nothing is
whitelisted by substring, so a new field is compared rather than waived.

With `--wasm` the comparer also decodes the import section using the verifier's reader —
deliberately not the generator's — and judges the regenerated table against that decode, so one
command answers both "does the regeneration match the committed pair" and "does this module
actually import what the table says". Without it the comparison still runs, but the ABI is not
fully verified and the verdict line says so. Exit 1 is a mismatch, exit 2 is bad usage.

CI runs the two as separate steps and keeps them separate on purpose: the comparison reads a
regeneration produced in the same job, while the checker reads the *committed* files, so a
generator that regressed cannot satisfy both by agreeing with itself.

### The glue is an input, not a constant

Two builds of the same engine are not byte-identical, and the difference is not cosmetic.

| file | bytes | sha256 (first 8) |
| --- | --- | --- |
| `ports/artemis/vendor/artemis-sdk/WebAssembly/asyncify/artemis.js` (tracked, vendor SDK) | 276,695 | `a3e65b92` |
| `.test/artemis-official-async/deploy/web/artemis.js` (a deployed build) | 276,697 | `f759f8b3` |

The first difference is at byte 4495: an embedded `adPackage` table reads `end:236` in the
vendor copy and `end:3817` in the deployed one. Everything after it shifts by a uniform
**+2**, so every `glueImplOffset` and every `impl` offset in this table moves by two bytes
between the two builds. Measured as a 2×2 matrix: vendor glue against the vendor-generated
table and deploy glue against the deploy-generated table both pass every check; the two
cross pairs each fail exactly the two offset checks, and nothing else.

The generated table therefore records the sha256 of both the module and the glue it was
made from (`totals.moduleSha256`, `totals.glueSha256`). Of the two, only the **glue** is judged:
a different glue is a refusal up front, one line naming both files instead of 405 "bad offset"
lines that read like a corrupt table.

The module hash is reported and not judged, and that is a measurement rather than a concession:
a module carries its own build directory inside the runtime's assert strings, so the same tree
gives **41,321,914 B** with `D:/online_gal/...` in it from a Windows checkout and **41,322,022 B**
with `/home/runner/work/...` from the runner. A byte comparison that included the module's own
hash could therefore only ever be satisfied by the machine that produced the committed table.
What the table claims — the import surface and every `impl` offset — is a function of the import
section and the tracked glue, both identical on every machine. `compare-imports-map.mjs` judges
exactly that: it compares the two tables field by field and masks the two provenance values
(`moduleBytes`, `moduleSha256`) alone, instead of subtracting them out of a diff.

So a failed identity check is not a defect in the table. Regenerate it for the inputs you
actually have:

```sh
node ports/artemis/harness/glue/imports-map.mjs \
  --wasm   <artifact-dir>/dist/artemis-bridge/build/bridge.wasm \
  --glue   <the artemis.js you are reading> \
  --aliases <artifact-dir>/dist/artemis-bridge/build/runtime-imports.json \
  --out-dir <where you want it>
```

`--out-dir` creates the directory if it does not exist.

**Which table do I read?** The one generated from the glue you are actually instrumenting.
If you are tracing a running browser page, that page is running the *deployed* glue, so its
offsets are the deploy glue's — the tracked vendor table is two bytes early for every
`impl` offset after byte 4495. Read the wrong one and you will open `artemis.js` at the
wrong place and conclude the code says something it does not. When in doubt, check
`totals.glueSha256` in the json against `sha256sum` of the file in front of you.

## Reading a row

`glue ref` is where the name is bound; `impl` is where the function behind it is defined,
and is the offset you want when you go read the body. The two are different places, and
the glue is minified onto a single line, so an offset really is the only stable locator —
a line number would be 1 forever.

`todo` means "not needed yet, and here is why" — the reason is on the row. `fd` is backed
by `@online-gal/vfs`, `gl` by the real WebGL2 context and AudioContext, and `async` is
the set of Asyncify re-entry trampolines a host has to unwind through rather than call
normally. The `modern owner` column says which module under
`packages/runtime-artemis/src/host/` decides each bucket, and it prefixes that with
`landed:` or `planned:` — read the prefix, not the path. A path alone reads as "done"
whether or not the file exists.
